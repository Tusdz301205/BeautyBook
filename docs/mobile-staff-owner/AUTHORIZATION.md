## Critical boundaries

- `booking:read:branch` assigned to STAFF is a coarse catalog capability. Personal assignment and live resource scopes are still mandatory. New list/detail enforce both in the query. Legacy booking detail now enforces assignment in `loadAndAssert`; Staff mutations recheck exact item after locking it.
- `rolesAtResource` binds lifecycle authority to current booking business/branch and expiry; Owner in A cannot reprice/resize or perform Owner lifecycle in B. Staff assignment is not check-in, assign, cancellation, request approval, or whole-booking completion authority.
- STAFF legacy booking list/detail/scheduler/mutation responses use allowlists: no service price, payment/refund amount, customer contact/profile/health note, employee emergency contact, or coworker actionable item. Safe appointment/service identifiers and planned/actual timing remain. Existing authorized legacy commission API was not removed; mobile never calls it.
- CUSTOMER and operational accounts remain separated in `auth/account-separation.ts`, `auth/auth-workspace.ts` and `AuthService.login`. SALON role choice comes from server scopes. BUSINESS_REQUIRED labels are loaded only after bcrypt succeeds; existing businessIds remain compatible. No public business enumeration endpoint was introduced.
- Owner request list intersects selected session business; approve/reject bind to the request booking's actual branch and corresponding approval permission. The optional `X-Mobile-Owner-V1:true` finance guard adds a transaction-local cancellation/rejection constraint, not new authority. It emits409 MOBILE_FINANCE_REVIEW_REQUIRED instead of exposing money or performing refund/benefit work.
- Notification targets carry context, not authority. Known impact Staff notification body contains the resolution label, not customer reason/contact/money. Self notification history is account-wide, so branch/business selection does not change unread count. Target opening must use authorized work query and tolerate reassignment/lost scope. Historical notification rows were not runtime audited.
- Owner onboarding fallback exists in multi-tenancy helpers only with verified BusinessOwnerProfile ownership; it does not grant Staff operational work. Owner without StaffProfile can use Owner mode. PLATFORM/Receptionist-only cannot enter personal work API.
